# TTTの概念から考えるAI設計

> **位置づけ:** ここに記す内容は、TTTの幾何学的語彙とネットワーク科学から着想したシステム設計案である。TTTから数学的に導かれた設計定理でも、脳や意識を再現するモデルでもない。性能・安全性は、個別の実装と評価で確かめる。

## 1. 設計の中心：AIは何を「見た」かを記録する

先行文書では、観測を「対象・装置・環境の相互作用」と「設定依存の観測写像」に分けた。この見方をAIに応用すると、AIの出力を単なる回答ではなく、**入力・文脈・使用した情報・不確かさ・選択した行動から作られた記録**として扱える。

AIの内部状態を完全に説明できると仮定するのではなく、各判断について次を記録する。

| 要素 | 記録する内容 | 例 |
| --- | --- | --- |
| 入力対象 | 何を解釈したか | ユーザーの依頼、画像、取得したファイル |
| 観測文脈 | どの制約・設定で処理したか | 対象期間、言語、許可されたツール |
| 根拠 | どの情報を出力に使ったか | 文書名、検索結果、データの行 |
| 不確かさ | 何が未確定か | 欠損、曖昧な参照、低い予測信頼度 |
| 行動 | 何を実行または提案したか | 回答、追加検索、外部変更の下書き |
| 結果 | 行動後に何が確認できたか | 成功、失敗、ユーザーからの修正 |

これは内面を完全に可視化する仕組みではなく、入力から出力までの**監査可能な記録**を作る設計である。

## 2. 小さな専門群と全体調整を組み合わせる

脳ネットワークとの対応は、脳の構造をAIにそのまま移植する主張ではなく、複数の処理単位をどう接続するかを考える類比として使う。

* **局所モジュール:** 検索、計算、文書読解、コード実行など、限定した役割を持つ処理器。
* **ブリッジ:** 異なるモジュール間で、必要な結果と出典だけを渡す接続。
* **調整器:** 依頼を分解し、必要なモジュールを選び、結果を統合する処理。
* **共有記録:** 依頼、制約、根拠、未解決点、完了状態を保つ短い状態表。

局所処理を分ければ専門タスクの混線を減らしやすい。少数の長距離接続は、個別結果を全体の目的に結び付けるのに役立つ。一方、調整器や共有記録を唯一の依存点にすると、そこが故障・誤解・攻撃の集中点になる。必要に応じて独立検査、再試行、停止時の安全な代替手順を設ける。

```text
依頼 ──> 文脈・制約の整理 ──> タスク分割
                                  │
              ┌───────────────────┼───────────────────┐
              v                   v                   v
          検索・読解          計算・分析           外部ツール
              └───────────────────┼───────────────────┘
                                  v
                       根拠・不確かさの照合
                                  v
                         回答または次の行動
                                  │
                                  v
                            結果の記録
```

### 2.1 接続を増やす前に「渡す情報」を決める

モジュール間の接続は、会話全文を無条件に複製するのではなく、受け手が判断に必要とする情報に絞る。受け渡し形式には、少なくとも「目的」「使った根拠」「確度・欠落」「次に必要な判断」を含める。個人情報や機密情報は、タスクに不要なら渡さない。

接続を動的に増やす場合も、エッジ数そのものを知能や性能の代理指標にしない。追加接続が有効かは、品質、遅延、費用、情報漏えい面の評価で判断する。

## 3. 観測文脈を明示して、出力を条件付きにする

同じ入力でも、対象期間、利用可能な資料、信頼基準、ユーザーの目的が違えば適切な回答は変わる。そこで各タスクに文脈レコード \(c\) を付け、出力を次のように扱う。

\[
y = f(x, c, E),
\]

ここで \(x\) は依頼、\(c\) はタスク文脈、\(E\) は利用可能な根拠である。これは汎用的な設計記法であって、TTTの既存方程式や物理法則ではない。

実装では文脈を暗黙のプロンプトだけに隠さず、構造化して保持する。

```yaml
task: "指定期間の資料から売上推移を要約する"
scope:
  period: "2024-Q1..2025-Q4"
  sources: ["sales.csv"]
constraints:
  currency: "JPY"
  missing_values: "補間せず明記"
evidence: []
uncertainties: []
proposed_action: null
```

重要な曖昧さが出力を左右する場合は、推測で埋めずに確認するか、複数の解釈を明示する。文脈が変わったときは、その変更と出力への影響を記録する。

## 4. 観測と行動を分離する

AIエージェントでは、情報を読むことと、外部状態を変更することを同じ段階にしない。

1. **観測:** 入力・ファイル・サービスから情報を読む。
2. **解釈:** 根拠と不確かさを整理し、候補を作る。
3. **計画:** 行動、期待される結果、失敗時の復帰策を定める。
4. **実行:** 許可されたツールで行動する。
5. **確認:** 実際の結果を読み戻し、完了を判定する。

読み取りと可逆的な作業は進められるようにし、送信・公開・削除など外部への重大な変更では、許可状態を明確に扱う。実行後は成功を推測せず、返された結果を確認して記録する。この段階分けは安全なエージェント実装の提案であり、TTT独自の保証を意味しない。

## 5. F={A, B, C}を使う場合の限定的な使い方

TTTの三項語彙をチームやエージェントの役割分担に使うなら、物理的・心理学的な実体ではなく**作業チェックリスト**として定義する。

| TTTのラベル | AI開発での仮の役割 | 確認する問い |
| --- | --- | --- |
| A（Acuteness） | 仕様、制約、検証 | 目的と合格条件は明確か。根拠は確認できるか。 |
| B（Buffoonery） | 代替案、探索、異論 | 見落とした解釈や反例はないか。 |
| C（Cunning） | 実装、運用、資源調整 | 実行可能か。副作用と復帰策は分かっているか。 |

ラベルを付けるだけで品質が上がるとは限らない。役割間の独立性を保ち、同一モデルの同じ誤りを複数役で反復していないかを評価する。必要なら外部データ、決定的な計算、別実装の検証を使う。

## 6. 評価計画

各設計案は、通常の単一処理構成を基準に比較し、少なくとも次の指標を記録する。

| 評価軸 | 例となる測定 |
| --- | --- |
| 正確さ | 正解率、数値誤差、出典との一致率 |
| 根拠の追跡性 | 回答の各主張に根拠が紐づいた割合 |
| 不確かさの扱い | 過信率、棄却／確認質問の適切さ |
| 頑健性 | 曖昧な入力、文脈変更、欠損データでの性能差 |
| 運用コスト | 遅延、トークン、ツール呼び出し回数 |
| 安全性 | 不要な情報共有、許可されない外部変更、復旧可能性 |

アブレーションでは、モジュール分割、ブリッジ、共有記録、独立検査を一つずつ外し、何が結果を改善したのかを調べる。平均スコアだけでなく、失敗例とタスク別の差も報告する。

## 7. 小さく始めるプロトタイプ

最初の試作は、検索・読解・検証の三つの役割を持つ単一アプリケーションでよい。

1. 依頼から目的、対象範囲、禁止事項を構造化する。
2. 検索役は出典付きの候補だけを返す。
3. 読解役は候補を要約し、根拠と未確定点を分ける。
4. 検証役は原資料を照合し、主張ごとに一致・不一致・未確認を付ける。
5. 調整器は未確認点が重要なら確認を求め、十分な場合だけ回答を作る。
6. 最終出力と使用根拠、残った不確かさを監査記録に残す。

この試作で改善が確認できた部分だけを残す。モジュール数やネットワークの複雑さを増やすこと自体を目標にしない。
